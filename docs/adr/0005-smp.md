# 0005 — A per-CPU SMP foundation, bootstrap-owned services

## Context

The kernel had a single scheduler, one bootstrap stack, and one local APIC timer.
Limine's MP protocol hands application processors to the kernel during boot, but
the kernel's shared IDT, address space, scheduler tables, and APIC mapping do not
exist until the bootstrap processor finishes its early boot path. Starting an AP
immediately would either fault or read bootloader memory that has already been
reclaimed.

SMP also raises a service-safety question. The kernel's file server, network
service, input driver, and display service are single-CPU state guarded by the
assumption that only the bootstrap processor mutates them. Making APs run those
services concurrently would turn every one of those single-CPU structures into a
race unless the whole service layer were redesigned.

## Decision

Implement SMP as a verified per-CPU foundation, not as concurrent service
scheduling:

- Limine's MP handover captures processor IDs and starts the APs.
- Each AP waits on a single atomic `SMP_READY` gate before it continues.
- Once ready, every AP installs its own kernel stack, fault stack, GDT/TSS pair,
  local APIC timer, scheduler, thread pool, and one kernel-only idle thread.
- The bootstrap processor remains the only owner of user processes, services,
  and drivers. APs never enter ring 3 and never touch the service or driver
  state.
- CPU identity comes from CPUID leaf 1 `EBX[31:24]`. The xAPIC ID register is
  read as zero on every CPU in QEMU, so it cannot select the per-CPU scheduler
  there; CPUID reports the IDs the bootloader snapshot already captures.
- The APIC timer is armed in periodic mode. Its handler acknowledges the
  interrupt on the delivering CPU and accounts that CPU's scheduler tick.
- The timer handler always resumes the interrupted thread through a saved
  register file. When no scheduler thread exists yet, it restores `r15..rax`
  and the interrupt frame instead of returning through the frame alone.

## Alternatives

- **Start APs before shared setup completes.** Rejected: the bootloader protocol
  pages and the kernel tables do not exist yet, so the AP's first instruction
  would fault before any diagnostic can explain it.
- **Use the xAPIC ID register as the CPU identity.** Rejected on the tested
  platform: QEMU reports zero for every processor's ID register. The architectural
  identity is available from CPUID leaf 1 and matches the boot snapshot.
- **Run services and drivers on all CPUs immediately.** Rejected for this phase:
  the service state is bootstrap-owned and not concurrency-safe. Claiming
  concurrent scheduling without redesigning that state would be an unverified
  claim.
- **Use a TSC-deadline APIC timer.** Rejected: the periodic timer is simpler to
  verify and already yields observable per-CPU scheduler ticks. The deadline form
  would add another per-CPU state dependency without proving more.

## Consequences

The system has real per-CPU scheduling, stack, TSS, and timer state, and the
`smp_cpu_state` suite checks that state from outside. It does not have concurrent
multi-CPU service scheduling, and the documentation says so explicitly. The
BSP-owned service model remains a deliberate limit rather than an accidental one.

The `-smp 4` QEMU path is the verification path. The bootstrap processor still
runs the in-kernel suite and the user-facing services; APs run only kernel-only
idle threads.

## Conditions that would reopen the question

- A service layer redesigned around per-CPU state, locks, message passing, or
  explicit ownership.
- A requirement to schedule user processes on APs, which needs per-CPU address
  space and service ownership rather than only kernel idle threads.
- A platform whose CPUID identity does not match the bootloader snapshot, or a
  platform with APIC ID values that are actually populated and authoritative.
- Hot-plug or processor removal, which the current fixed `MAX_CPUS` table does
  not model.
