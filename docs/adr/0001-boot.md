# Boot through Limine, pinned and verified

- Status: Accepted
- Date: 2026-10-22

## Context

NovaOS needs a bootloader, and writing one is not the project. The bootloader
has to do three things this kernel depends on: place a bare-metal ELF64 image
in memory, hand over a memory map, and provide a window onto physical memory
that the kernel can use before it has page tables of its own. Everything else
about the boot chain is a decision about who is responsible for what.

The design report recommends UEFI plus Limine, and names "writing a UEFI
loader" as the alternative to be rejected. That recommendation is right, but
the interesting part is not *which* bootloader — it is that a bootloader is
the first thing to execute with full privilege, before any of the kernel's own
checks exist. Every property the boot chain relies on therefore has to be
established by something other than the kernel's integrity.

There is also an environment fact that shapes the choice. `/dev/kvm` does not
exist in the reference environment, so QEMU runs under TCG. A full boot takes
about seven seconds. That is slow enough that the boot path has to be cheap to
iterate on, and slow enough that a *hang* and a *slow boot* are easy to
confuse.

## Decision

The kernel boots through **Limine**, at a pinned release, and the boot
protocol revision is checked explicitly.

* The pinned release is `12.9.4`, and the release archive's SHA-256 is
  recorded in `tools/xtask/src/limine.rs` and verified after download. The
  checksum is intentionally *not* fetched at runtime: verifying an artifact
  against a checksum fetched from the same host verifies nothing. A
  bootloader is the first thing to execute with full privilege, so an
  unverified download would make every other check in the system advisory.
* Three things move together and must not drift: the boot protocol revision
  the kernel implements, the release that speaks it, and the bootloader
  configuration format. Limine 12 reads 12.x paths and writes 12.x protocol
  structures, so an unpinned "latest" would change the path syntax and the
  response layout underneath a kernel that had not changed.
* The kernel asks for the base revision and **panics** on a mismatch, before
  any hardware access, so a mismatch is a clean diagnostic rather than a
  machine that dies before it can speak.
* The image carries both the BIOS and the UEFI Limine binaries, so one ISO
  boots under either firmware. OVMF requires a dual-pflash configuration; the
  `-bios` path is a debugging alternative, not the primary one.
* The boot protocol's *requests* are discovered by exported symbol name, not
  by section.

### Why the discovery mechanism matters enough to be a decision

Limine 12 locates the kernel's requests by scanning the ELF symbol table for
names beginning with `LIMINE_`. It does **not** look for a section. The
earlier revision of this kernel placed the requests in a linker-designated
`.boot.rodata` section, which is how the protocol worked in Limine 11 and what
most guides still show.

The failure is completely silent and it fails in the most confusing way
available. The bootloader loads and starts the kernel perfectly well, the
kernel runs, and then:

```text
[NOVA] ERR   | panic: limine: bootloader too old; base revision 3 or newer is required
```

appears. That message is not about the bootloader being old at all — Limine
12.9.4 supports revision 6. It is the base-revision response still holding
its initial value because Limine never found the request to fill in. The
diagnostic points at the bootloader when the bug is entirely in the adapter.

So the request declarations are `#[unsafe(no_mangle)] pub static` items whose
*symbol names* begin with `LIMINE_`, and that is the entire discovery
mechanism. Renaming a symbol or dropping `no_mangle` breaks boot with no
build error to explain it. The `.boot` section is still kept, but for a
different reason: it pins the requests into one contiguous, page-aligned run
that the bootloader can treat as a unit. It is a convenience, not the
discovery mechanism.

### Why the bootloader does not survive the handover

Limine's response structures live in bootloader-owned pages that the
bootloader may reclaim as soon as it hands over control. The adapter
therefore copies everything the kernel needs into kernel-owned storage during
`boot::capture` and performs no access to a `Request::response()` pointer
afterwards. Every later stage reads the published snapshot.

This is not defensive style. It is the difference between a kernel that
sometimes reads garbage and a kernel that never does, and the cost of getting
it wrong is a fault whose faulting address points at a page the kernel has
never heard of.

### The three traps worth recording

Each of these was found by bisecting QEMU's behaviour rather than by reading
the documentation, and each fails silently.

1. **The config format changed wholesale.** Limine 12 entries open with
   `/Title` (not `:label`), the protocol name is `limine` (not `elf64`),
   `timeout: 0` means "boot instantly without showing the menu", and `no`
   means the opposite. `default_entry` must be the bare entry name — a
   leading `/` is parsed as an empty first component and silently disables
   autoboot. Any one of these wrong produces no build error and no error
   message: Limine prints `[config file contains no valid entries]` and waits
   at its menu. The harness then reports a timeout, which reads as a kernel
   hang.
2. **A `module_path` naming a file that is not on the ISO voids the whole
   entry.** The line is emitted only when the initramfs is actually staged,
   so a missing module is a recoverable degradation rather than an unbootable
   image.
3. **The console must exist before anything that can panic.** The panic
   handler prints through the console, and an uninitialised console discards
   the write. The symptom is "exited in a panic state with an empty serial
   log" — the panic message is lost by the very code that would have
   reported it.

### Why the exit path is part of the boot contract

The kernel signals the end of a test run by writing to QEMU's
`isa-debug-exit` device. That device listens on whatever `iobase=` says; it
has no fixed port. Writing to the wrong port means the kernel finishes its
tests, writes to a port nothing is listening on, and QEMU keeps running — a
symptom indistinguishable from a hung kernel. `scripts/qemu.sh` therefore
asserts its own copy of the port against the kernel's source rather than
trusting the copy, so a change to either that is not made in both fails
loudly at startup.

`-no-reboot` also matters for correctness of the *result*: it turns a reset
into a successful QEMU exit, so a kernel that triple-faults before printing
anything would be reported as a pass. The boot path therefore has to be able
to say what happened, not merely whether the machine stopped.

## Alternatives

**A hand-written UEFI loader.** Rejected. It would have to parse the UEFI
service tables, load the kernel, build page tables, and hand over a memory
map — each of which is a place to get a subtle error wrong, none of which is
the project's purpose, and all of which would need its own debugging
harness. The alternative Limine offers is a bootloader that has been
debugged by many people, and the cost is only that its behaviour has to be
learned.

**GRUB.** Rejected for a reason that is about packaging rather than
philosophy: `grub-mkrescue` introduces a second bootloader into the chain
and needs a loop device that is not always available in a container. There is
exactly one bootloader in this chain, and it is Limine.

**A multiboot or Linux boot protocol.** Rejected. They are shaped for
loading an operating system with a conventional memory layout and a
conventional console, and neither of those is what NovaOS wants: the direct
map's *offset* is a property this kernel uses, and a protocol that does not
report one would leave the kernel guessing where physical memory is.

**Booting Limine from a disk image with a partition table.** Deferred. The
first release ships an ISO with an El Torito catalog, which boots under both
OVMF and SeaBIOS and needs no partition table.

## Consequences

The kernel boots in about seven seconds under TCG, which is slow enough that
iteration needs the automated harness and the interactive script to be two
separate things: `cargo xtask run` is non-interactive and decides pass or
fail, and `scripts/qemu.sh` is for looking at a hang.

Limine's version becomes a dependency with a real blast radius. A Limine
release that changes its configuration format or its protocol revision will
break the boot in ways whose diagnostics point away from the cause. That is
why the revision is checked explicitly and why the request discovery is
documented here rather than left as an implementation detail.

The three traps cost real time to find, and each of them produces *no*
diagnostic. The lesson generalises beyond Limine: **a boot chain's failures
are silent, so the checks have to be assertions rather than diagnostics.**
The consequence is that the boot path carries more explicit assertions than
the rest of the kernel.

## Validation

* `cargo xtask run` boots the image under QEMU and prints the kernel's
  version banner.
* `cargo xtask test` distinguishes a failure from a timeout, so a boot that
  never enters the kernel cannot be reported as a pass.
* The Limine configuration's shape is asserted by host-side tests in
  `tools/xtask/src/boot.rs`, including the rule that no slash may appear
  above the entry opener — the one assertion that can tell a correct
  configuration from one that merely looks correct.
* The exit port is asserted across the shell script and the kernel source.
* The request-discovery mechanism is documented in
  `kernel/src/boot/limine.rs` next to the code that depends on it, and
  `readelf -sW` on the built kernel is the check that the requests are
  really exported.

## Revisit When

* A second architecture needs a boot path that Limine does not serve, or
  Limine's AArch64 support proves insufficient for the target hardware.
* A real machine replaces QEMU as the primary test environment, and its
  firmware's boot behaviour differs enough from OVMF's to matter.
* The boot chain needs to carry something Limine does not provide — a second
  stage, a signed image, a chain of trust from the firmware.
* A hardware target arrives that has no usable UEFI and no legacy BIOS, in
  which case the "one ISO boots under either firmware" property stops being
  the reason to ship both binaries.
