# NovaOS architecture ports

## Symbian EKA2 source review

- EKA2 keeps the nanokernel thread state in `NThreadBase`. `NTimerQ::Tick` and `TDfc` distinguish interrupt-time work from deferred execution. NovaOS uses architecture-specific trap and timer entry with portable scheduler state in `nova-core`. The early ports exercise the interrupt path from user mode. [Thread source](https://github.com/cdaffara/symbiandump-os1/blob/master/sf/os/kernelhwsrv/kernel/eka/nkern/nkerns.cpp) · [Timer source](https://github.com/cdaffara/symbiandump-os1/blob/master/sf/os/kernelhwsrv/kernel/eka/nkern/nk_timer.cpp) · [DFC source](https://github.com/cdaffara/symbiandump-os1/blob/master/sf/os/kernelhwsrv/kernel/eka/nkern/dfcs.cpp)
- EKA2 distinguishes `NFastMutex` from `TSpinLock`. NovaOS separates blocking, physical-word-keyed futex waits from short, interrupt-masked kernel spin locks. A remote wake queues work for the owning scheduler and signals it by IPI rather than modifying its run queue. This does not imply EKA2 binary compatibility, priority inheritance, or owner-death recovery.
- EKA2 has explicit client/server delivery and completion. `TMessageBase::SendReceive` parks the sender until completion. NovaOS keeps bounded messages, endpoints, and one-shot reply authorization in `nova-ipc`. Its x86-64 kernel connects IPC completion to the scheduler and runs service integration tests. [Message source](https://github.com/cdaffara/symbiandump-os1/blob/master/sf/os/kernelhwsrv/kernel/eka/kernel/server.cpp)
- The flexible memory model gives processes an address-space object whose identifier and virtual reservations have their own lifetime. NovaOS adopts separate translation roots, explicit page permissions, and scheduler-controlled activation. AArch64 switches between distinct stack mappings at the same user virtual address. [Process source](https://github.com/cdaffara/symbiandump-os1/blob/master/sf/os/kernelhwsrv/kernel/eka/kernel/sprocess.cpp) · [Address space source](https://github.com/cdaffara/symbiandump-os1/blob/master/sf/os/kernelhwsrv/kernel/eka/memmodel/epoc/flexible/mmu/maddressspace.cpp)

## Emulated platforms

- **x86-64** uses NovaBoot under OVMF and four-level PML4 paging. The ring-3 suite runs the IPC client and server on separate CPUs, checks a write protection fault after a remote permission downgrade, and checks private address-space reclamation on normal exit and on faults. Shared-memory destruction removes mappings and waits for remote TLB acknowledgements before returning frames to the allocator.
- **AArch64** uses PL011 and GICv2 on QEMU `virt`. EL0 uses four-level L0–L3 translation with 4 KiB pages. Tests cover `svc`, the virtual timer, and NEON, floating-point and TLS state across context switches. PSCI starts secondary CPUs; GIC SGIs signal scheduler work.
- **RISC-V 64** uses OpenSBI and QEMU `virt`. Tests cover U-mode under four-level Sv48, `ecall`, the supervisor timer, and scalar and optional vector state. SBI HSM starts secondary harts; SBI IPIs signal scheduler work.
- **LoongArch 64** uses the QEMU `virt` direct ELF entry. PLV3 uses a four-level software TLB refill while PLV0 uses direct addressing. Tests cover `syscall`, the processor timer, scalar floating-point state and condition codes, and LSX/LASX when available. IOCSR mailboxes start and signal secondary CPUs.

`cargo xtask test-ports` runs four-CPU trap and scheduler checks, plus resident service checks with one and four CPUs. The guests discover early RAM and CPU IDs through the device tree. The four-CPU checks require three secondary user schedulers, a cross-CPU futex wake IPI, and 128 capability RPC replies between the resident init on the bootstrap CPU and echo server on the first secondary CPU. The harness fails on a guest failure, panic, missing result or timeout.

The `virt` loader maps multi-page ELF load segments as RX, R/NX, or RW/NX inside a fixed 2 MiB user window, with a budget of eight private pages including the stack. It zeroes private frames before copying file-backed bytes. The trap checks reject writes to code and read-only data, execution from RW data, and reads from the stack guard. After the probes exit, each CPU checks that the allocation bitmap has returned to its original state. IPC payloads and reply tokens can span two pages; the kernel checks both fragments before consuming a message or accepting a call.

The LoongArch checks require QEMU **10.2.2 or newer**, or a build with the equivalent PNX exception fix. QEMU 10.2.1 tries to read the instruction that caused an NX fault, raising the same exception again before guest exception delivery. Use the fixed emulator on `PATH`; the CI job builds 10.2.2 from the upstream release. [QEMU exception handler](https://github.com/qemu/qemu/blob/v10.2.2/target/loongarch/tcg/tcg_cpu.c)

The `virt` implementations are early runtimes, not ports of the complete x86-64 system. Their address spaces have one CPU owner, and local invalidation is not a substitute for a cross-CPU TLB shootdown. They do not implement general process creation and supervision, migration, multi-CPU address-space ownership, or the full device, storage, network and desktop stack. None of the four targets has been qualified on physical hardware.

## System completion criteria

1. Define the platform boot contract for each architecture. Discover RAM and reserved ranges from firmware and device trees or ACPI. Feed that data into an allocator and architecture-specific page-table backend. Test unmapped and permission faults, process teardown, and TLB invalidation across cores.
2. Connect the common scheduler and syscall dispatcher to each architecture's trap frame. Preserve integer, FP, SIMD and TLS state. Test repeated preemption, fault containment, inter-processor interrupts, idle wakeups, and SMP scheduling.
3. Load a native ELF init process from an initramfs and grant it handles through the capability table. Boot the same client/server integration workflow across all four platforms. Run IPC, service supervision, driver, and filesystem tests through the public ABI.
4. Support firmware, interrupt, timer, storage, and network drivers on named physical machines. Verify boot, I/O, shutdown, and recovery on each one. QEMU checks cover emulated hardware.
